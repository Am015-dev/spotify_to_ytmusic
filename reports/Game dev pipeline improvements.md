# Stop waiting, start spawning: faster Overdrive builds

Big studios iterate quickly by keeping every experiment cheap. They confirm an idea with a throwaway mock-up before building it, check each change with tests that take seconds, keep tuning values in data rather than code, and save slow play tests for release candidates. Mainhattan Overdrive has worked the other way round. Every change waited on one 17–70 minute play test, eight workers ran in parallel on one 3 MB file, and a $50 track builder went ahead without a cheap mock-up first. Today that added up to **~$121 spent, ~70% of worker time spent waiting, and no release shipped**. Today's new rules (10-minute slices, checklist tests first, a 1-minute dry run, one screenshot pass, the long test only for release candidates) already fix the biggest leak. The next big win is to make the in-game checklist **GO buttons pass or fail automatically in seconds**, which is how Rare tests Sea of Thieves. After that come a confirm step before any feature over about $5, a tuning panel Alex can use on his phone, and a world builder that places tracks inside Frankfurt and Athens rather than on an empty flat plane. The ranked TOP 10 table is at the end.

## How studios work, and where we differ

Studios kill most ideas while they are still cheap. Supercell said that of its last 10 games, only Clash Royale reached a worldwide release, and seven were dropped at the prototype stage ([GDC Vault](https://gdcvault.com/play/1023160/contactUs); [wnhub](https://wnhub.io/news/other/item-11070)). Nintendo tested Breath of the Wild's physics ideas in a **2D 8-bit prototype** before full production ([TechRaptor](https://techraptor.net/content/8-bit-zelda-breath-of-the-wild-prototype)). Valve treats each design as a guess and each playtest as the experiment that checks it, and says playtests aim at fun, "not bug testing" ([Valve GDC 2009](https://cdn.fastly.steamstatic.com/apps/valve/2009/GDC2009_ValvesApproachToPlaytesting.pdf)). During Halo 3, Bungie ran a **playtest every afternoon** ([Killscreen](https://www.killscreen.com/competitive-gaming-winning-cost-games/)).

The track builder is the clearest example of the gap. Nobody showed Alex a mock-up or a 30-second clip first, so the "flat, boring" verdict arrived after **$50** had been spent instead of after $2. Anthropic's own guidance for coding agents points the same way. Larger features should start with a written spec "that name[s] the files… state[s] what is out of scope, and end[s] with an end-to-end verification step". Agents also need a check they can run, because without one "'looks done' is the only signal available" ([Claude Code best practices](https://code.claude.com/docs/en/best-practices)).

Running many workers at once is also costly for this kind of work. Anthropic measured multi-agent systems using about **15× the tokens of a chat** and calls them a poor fit for coding, where tasks share context ([Anthropic engineering](https://www.anthropic.com/engineering/multi-agent-research-system)). That matches the project's own rule of one fix worker plus one integrator, which the eight workers broke today. Expectations also need calibrating. In METR's 2025 study, experienced developers using AI tools took **19% longer** while believing they were 20% faster ([DX summary](https://getdx.com/blog/metr-study-on-how-ai-affects-developer-productivity/)). Speed has to be measured, not assumed.

## Testing: replace one long drive with many 1-second checks

Rare's Sea of Thieves team ran **over 23,000 tests**. About **70% were "actor tests"**: tiny scenes that create just the one thing being tested, advance it by hand and check the result, taking up to a tenth of a second each. Full-level tests took **~20 seconds** and were kept to 5%, covering only the main success path. The slow screenshot and performance tests ran rarely, often overnight. The result was that checking a build dropped from **10 days to 1.5 days**, and the number of full-time testers fell from **50 to 17** ([Masella, GDC 2019](https://media.gdcvault.com/gdc2019/presentations/Masella_Robert_AutomatedTestingOf.pdf)). Rare is also clear that automation cannot judge fun: "how the game feels to play really can't be done by an AI" ([same](https://media.gdcvault.com/gdc2019/presentations/Masella_Robert_AutomatedTestingOf.pdf)).

Alex's checklist idea, with GO buttons that spawn just the requirement, is Rare's actor test. It is half built. The GO buttons already spawn the scenario. What is missing is an automatic **PASS/FAIL check with the measured number** shown on screen, and a way to run the whole checklist without a person. Two technical blockers stand in the way. The game's clock follows real time, and it calls `Math.random()` **104 times** with nothing to make the results repeatable. As a result, a 30-second scenario takes 30 real seconds and gives slightly different results each run. A fixed-step "advance N frames" hook and a seeded random number generator remove both blockers. Gaffer on Games explains why a fixed time step is the only way to get identical replays ([Gaffer On Games](https://gafferongames.com/post/fix_your_timestep/)). The three.js project itself takes golden screenshots of every example once randomness is frozen, allowing **0.1% of pixels** to differ ([three.js e2e](https://raw.githubusercontent.com/mrdoob/three.js/dev/test/e2e/puppeteer.js)).

The resulting test ladder looks like this. All budgets are targets and have not been measured yet.

| Tier | What it checks | Budget | When |
|---|---|---|---|
| Static | Loads, 0 console errors, size cap, changelog entry | ≤20 s | every slice |
| Checklist spawn tests | One requirement each (tyre gap, wall slide, humanoid scale, HUD overlap) | ≤0.5 s each, ≤60 s total | every slice |
| Scripted drives | Bot drives a fixed loop and checks wall hits/min and stuck % | ≤15 s each | every slice |
| Golden screenshots | Start, Frankfurt, Athens, side view, garage | ≤30 s | every slice |
| Real-input play test | tPlay, ≤3 min per city | ≤5–6 min | release candidates only |

"Feel" still needs numbers. The game should report its own **wall hits per minute, % of time stuck, longest stuck stretch, airtime, and steering reversals per second**. The same numbers then come from a bot run, from tPlay and from Alex's own drive. EA used "times stuck" and path time to grade its vehicle bots ([EA SEED](https://www.ea.com/seed/news/seed-ml-research-aaa-game-testing)). Flaky tests should follow Rare's rule: retry once, set aside after repeated failures, and delete if still unfixed after a week.

iPhone-specific bugs stay hard to catch from the cloud. Playwright's WebKit mode can catch layout problems such as BRAKE overlapping GAS, but it is not real iOS Safari ([BrowserStack guide](https://www.browserstack.com/guide/playwright-ios-automation)). Real-iPhone runs on BrowserStack exist ([BrowserStack](https://www.browserstack.com/press/browserstack-becomes-the-first-platform-to-enable-playwright-testing-on-real-ios-devices-with-safari)), but they are only worth it for release candidates.

## World builder: build tracks into the cities, not onto a flat plane

Every successful racing builder does three things. Pieces always snap together, tracks sit inside an interesting existing environment, and nothing can be published until someone has driven a lap. Hot Wheels Unleashed designed its environments first and then added "gameplay hooks" to build around. Its players made **more than 500,000 tracks**, and every track must be driven by a large "Tractor" vehicle to catch impossible jumps ([Game Developer](https://www.gamedeveloper.com/design/a-closer-look-at-hot-wheels-unleashed-2---turbocharged-track-builder)). Trackmania uses a coarse **32 × 32 × 8 grid** and requires the author to finish the track before publishing ([Openplanet](https://openplanet.dev/plugin/advancedfreeblockmode); [doc.trackmania.com](https://doc.trackmania.com/play/what-is-totd/)). ModNation Racers lets players drive out a road over terrain they can sculpt, with shortcuts that leave and rejoin the road ([PlayStation Blog](https://blog.playstation.com/2009/12/23/modnation-racers-track-studio-walkthrough-with-track-designer-mark-riddell/)). LEGO 2K Drive's own designers say "our races live in the world" ([Press Start](https://press-start.com.au/features/2023/04/25/how-lego-2k-drives-open-world-driving-puts-fun-at-the-forefront/)).

That points to the cause of "flat, boring". The rejected builder made a walled ribbon on an empty plane. The fix is a hybrid placed inside Frankfurt and Athens: **8 m snap pieces with 2 m height steps** (the same 1:4 ratio as Trackmania, giving a 14° default ramp) on top of terrain that can be driven everywhere. Run-off areas should slow the car down instead of walls stopping it. Track-design guidance from the SuperTuxKart project supports **height changes and risky shortcuts** ([SuperTuxKart](https://supertuxkart.net/Making_Tracks:_Advanced_Gameplay_Design)), and Trackmania requires that players can respawn from every checkpoint. Measurable fun targets could include at least 3 climbs of 4 m or more per lap, one jump with 0.6–1.5 s of airtime, and no straight longer than 6 s. These numbers are our proposal; no studio publishes them. Before any of this is built, a **one-hour throwaway mock-up** should go to Alex for a yes or no.

## Libraries and GUIs: small tools, not big editors

None of the full editors (Needle, PlayCanvas, the React tools) fits without a rewrite, and Needle is paid for commercial use ([Needle pricing](https://needle.tools/pricing)). The useful pieces are small:

| Tool | Use | Cost |
|---|---|---|
| **lil-gui** | Phone tuning panel behind `?dev=1`, with a "Copy tune.json" button | **7.8 KB gz**; 0 bytes in the normal build if lazy-loaded ([npm](https://registry.npmjs.org/lil-gui)) |
| **three-mesh-bvh** | Collision against the real visible meshes, so walls match what you see | Pure JavaScript, MIT, released 2026-10-08 ([npm](https://registry.npmjs.org/three-mesh-bvh)) |
| **esbuild** | Replaces the shell-script build; splits files automatically and lazy-loads Athens and the garage | Rebuild in under a second (vendor speed class, not measured here) ([Better Stack](https://betterstack.com/community/guides/scaling-nodejs/esbuild-vs-vite/)) |
| **gltf-transform + LDraw** | Converts real LEGO part models to compressed `.glb` once, offline | CLI, MIT ([gltf-transform](https://gltf-transform.dev/cli); [LDrawLoader](https://threejs.org/docs/pages/LDrawLoader.html)) |

A full physics engine is not worth it now. Rapier has the only ready-made three.js vehicle example, but it weighs **1.65 MB gz**, about 45% of the 3.6 MB file cap, and adopting it would mean rewriting the driving feel Alex has been scoring ([three.js example](https://threejs.org/examples/physics_rapier_vehicle_controller.html)).

The asset GUI Alex needs is a `?viewer=1` page rather than a 3D editor. It would show a grid, a 1.8 m human outline and the car, with dimensions printed. A build check would also fail any model outside its expected size, since LEGO's LDraw units are fixed (1 LDU = 0.4 mm). That turns the "giants" bug, reported wrongly as fixed twice, into a check that runs automatically.

For game design, a **Google Sheet published as CSV** and converted to `tune.json` would let Alex edit cars and missions from his phone. Two links (`?ab=steerA` and `?ab=steerB`) would let him compare two versions of the driving feel side by side. Neither needs a server.

## Other levers: smaller files for agents, a shorter CLAUDE.md

CLAUDE.md records that **99.8% of tokens were context re-reads**, and that every new session spends **~150k tokens** reading the 3.7 MB file. Splitting the game into about 10 system modules of under 100 KB each (car, collision, Frankfurt, Athens, traffic, HUD, audio, tuning, models), with an index file, lets a worker read only the part it is changing. Anthropic also warns that "bloated CLAUDE.md files cause Claude to ignore your actual instructions" and advises moving must-always-run rules into hooks ([Claude Code best practices](https://code.claude.com/docs/en/best-practices)). The changelog and deploy checks fit that pattern. A **small in-game event log** (wall hit, stuck, flip, reset, with position) shown as dots on the minimap, plus a "Copy report" button, would turn "I crashed on every turn" into a trace the team can replay.

## Conclusion

The cost problem is a waiting problem, not a coding problem. Money leaks wherever a worker sits idle on a long test or builds something nobody confirmed. Today's rules stop the first leak. Automatic checklist tests make every slice self-checking in about a minute, and a $2 mock-up before any feature over about $5 stops the second. One gap remains: the project's standing order says workers never ask Alex anything, yet the track-builder loss shows that one yes/no question per feature, asked by the coordinator, is cheap insurance. A sensible target is **≤$40 per shipped release, $0 spent on rejected features, and worker waiting time under 20%**. Start measuring these numbers now, because today's test durations and build times have never been formally measured.
